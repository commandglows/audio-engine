# Runtime Resilience Contract

The current engine evolves capture without invalidating readable version 1
sessions. The portable lifecycle, segmented WAV session format, bounded
recovery, timestamps, and Flutter diagnostics implement the contract below;
physical route/unplug/suspension evidence remains a release gate.

## Device manager

`AudioDeviceManager` defines the portable selection model. Current platform
adapters open the operating-system default input and expose stable status
snapshots containing:

- stable engine ID, display name, platform backend, and route type;
- input channel descriptors and default channel selection;
- supported/native sample rates, sample formats, and buffer sizes;
- hardware timestamp coverage, native xrun support, and timestamp-query
  failures;
- permission/availability state and stable error code;
- preferred setup, effective setup, and explicit fallback reason.

Persisted preferences identify intent, not a promise that a device still
exists. If reopening the preferred setup fails, the manager tries the current
system default and emits a fallback event. It never silently rewrites the
preferred setup.

## Real-time callback

The capture callback receives preallocated destination capacity and a compact
`AudioCallbackContext`:

- monotonic host timestamp in nanoseconds when available;
- continuous engine frame position;
- frame count and negotiated format;
- native xrun counter snapshot when available;
- lifecycle generation incremented after every device reopen.

The callback may copy frames and update lock-free counters only. It may not
allocate, lock, log, call Flutter, access the filesystem, encode, resample, or
perform network work.

## Metrics

These counters remain distinct:

- `nativeXruns`: under/overruns reported by the operating system;
- `ringOverflowFrames`: frames rejected by the engine FIFO;
- `timestampGapFrames`: frames inferred missing from the monotonic timeline;
- `discontinuityEvents`: explicit discontinuity flags from the backend;
- `writerStalls`: storage operations exceeding the configured deadline;
- `deviceRestarts`: successful reopen generations after initial start;
- `routeChanges`: effective input route changes;
- `hardwareTimestamps`: successful native timestamp observations;
- `timestampQueryFailures`: failed native timestamp queries;
- `clippedSamples` and peak/RMS levels calculated off the real-time thread.

No aggregate `dropout` number may erase the source of a failure.

## Session v2

A session directory contains an append-only journal and independently playable
WAV segments. Each finalized segment is closed, synced, checksummed, and then
committed to the journal. Journal records include:

- session start/stop and completion state;
- effective device capabilities without a personally identifying device name;
- negotiated format, clock origin, and continuous frame positions;
- segment path, frame range, byte length, and SHA-256 digest;
- pause, gap, route-change, restart, warning, and failure events.

Recovery trusts only complete journal records and valid WAV headers. It may
repair a trailing WAV length field or discard a partial frame, but never edits
an already committed segment. Version 1 PCM sessions remain recoverable.

## Capture and DSP representations

The capture master preserves the negotiated lossless native PCM/float format.
A worker thread may convert committed blocks to planar float32 for meters,
waveforms, monitoring, and future DSP. That processing bus has its own bounded
queue and may drop derived work without ever blocking or damaging the master.

## Pause and interruption semantics

- User pause closes the current segment and journals an intentional gap.
- Platform interruption closes or checkpoints the segment and journals its
  reason; explicit resume starts a new lifecycle generation.
- Device loss triggers bounded fallback/reopen attempts and an explicit gap.
- Stop drains capture, finalizes the segment, commits completion, and only then
  reports `stopped`.
- A process death never produces a false `complete=true`.

## Promotion gates

No backend becomes the ContentGlows default until it passes:

- two-hour continuous capture with zero ring overflow;
- forced process death and deterministic recovery;
- screen lock/background and platform interruption;
- preferred/default-device loss and default-device fallback;
- low-storage failure without corrupting committed audio;
- independently playable segments and checksum verification;
- diagnostics matching the physical scenario and no sensitive identifiers.
