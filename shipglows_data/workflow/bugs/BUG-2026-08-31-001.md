# Bug Record: BUG-2026-08-31-001

## Summary

- Title: Android exhausts reconnect before a Bluetooth SCO headset returns
- Current status: `closed`
- Severity: `high` because it blocks the physical release-candidate recovery gate.
- Owner: sg-bug
- Next command: `/sg-bug --ship BUG-2026-08-31-001`

## Reproduction

- Preconditions:
  - Install commit `114232514c718381ca7750ad9e2fb2a5c769309e` on Samsung `SM-G996U1`, Android 15/API 35.
  - Grant `RECORD_AUDIO` after installation.
  - Connect and explicitly select Bose QC35 II as the Bluetooth SCO input.
  - Start a distinct recording session and wait for at least one finalized, non-silent WAV segment.
- Steps:
  1. Power off the Bose while recording.
  2. Power it back on immediately, as quickly as physically possible.
  3. Observe the journal/status through the five native reconnect backoffs and until Android restores Bluetooth.
- Reproducibility: failed in both physical sessions `1788180843806126` and `1788182060925494`; the second used immediate power-on.

## Expected Behavior

- The active recording remains in a recoverable interruption state for a realistic Bluetooth-profile return interval.
- When the same selected Bose SCO endpoint becomes available, Android restores the communication route, Oboe opens that endpoint (never the internal microphone), the journal records `device_restart`, and non-silent frames resume in new segments.
- Stop/background interruption remains bounded throughout recovery.

## Observed Behavior

- Android/Oboe retry only after fixed sleeps of `100`, `200`, `400`, `800`, and `1600` ms: 3.1 seconds of scheduled delay plus open-call time.
- Both physical runs reached `device_reconnect_exhausted` before Android restored the Bose Bluetooth SCO profile, including immediate headset power-on.
- The later Bluetooth return cannot recover the failed session.
- The release-candidate disconnect/reconnect gate remains red. No silent fallback to the internal microphone was observed.

## Evidence

- Physical session IDs: `1788180843806126`, `1788182060925494`.
- Code pointer: `flutter/shipglows_audio/android/src/main/cpp/android_oboe_capture.cpp`, `AndroidOboeCapture::RecoveryWorker()`.
- Route ownership pointer: `flutter/shipglows_audio/android/src/main/kotlin/com/commandglows/shipglows_audio/ShipglowsAudioPlugin.kt`, `selectCommunicationRoute()`.
- Existing policy tests: `tests/interruption_bench.cpp` and `tests/engine_tests.cpp` assert the current five-delay exhaustion contract but do not model a Bluetooth endpoint that appears after 3.1 seconds.

## Regression-First Correction Contract

1. Add a deterministic recovery-policy test where the selected endpoint is unavailable beyond 3.1 seconds, becomes available within the supported recovery deadline, and succeeds without exhausting or accepting a different device.
2. Add deterministic cancellation cases at the zero/first, boundary, and late-recovery waits; Stop must wake recovery promptly rather than wait through an uninterruptible sleep.
3. Make Android endpoint availability and SCO communication-route readiness explicit inputs to recovery. Kotlin should observe audio-device changes, reacquire the selected physical endpoint using retained identity rather than assuming the old numeric ID remains valid, reapply the SCO communication route, then allow native reopen against the current ID.
4. Use one documented elapsed-time deadline suitable for real Bluetooth profile reconnection, with bounded/cancellable polling or event wake-up. Exhaust only after that deadline; do not merely increase the fixed attempt count invisibly.
5. Preserve the invariant already added in `1142325`: a replacement stream succeeds only when its actual device matches the currently resolved selected input; never fall back to the internal microphone.
6. Retest on the physical Samsung/Bose pair and require `device_restart >= 1`, `routeChanges >= 1`, resumed frames, non-silent WAV data, Bluetooth SCO confirmed by AudioFlinger, recoverable `automatic_reconnect`, and no internal input.

## ZOMBIES Coverage

- Z — Stop before or during the first wait; no reopen and a prompt structured stop.
- O — One disconnect and one endpoint-return event recover exactly once.
- M — Duplicate device callbacks/open failures do not create concurrent workers, duplicate restarts, or overwrite segments.
- B — Endpoint return just before, at, and just after the elapsed-time deadline; exact exhaustion semantics remain deterministic.
- I — Kotlin owns Android device/communication-route readiness; native capture owns verified Oboe stream replacement; the handoff carries the current resolved ID and never trusts stale identity silently.
- E — ID changes, SCO output appears after input, route activation fails, Stop/background occurs during backoff, and the deadline expires.
- S — Implement one cancellable deadline-driven recovery state machine; avoid parallel independent retry loops in Kotlin and C++.
